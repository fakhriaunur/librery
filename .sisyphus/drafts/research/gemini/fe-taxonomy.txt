Librery: Frontend Architectural Taxonomy1. Core Philosophy: The Anti-Duplication MandateLibrery strictly avoids duplicating domain logic across different languages. The Functional Core is written once in pure Rust. Frontends adopt either the full FCRS (Functional Core, Reactive Shell) pattern or act strictly as a Reactive Shell (RS) based on their offline operational requirements.2. Patron OPAC & Dashboard (SvelteKit)Pattern: Pure Reactive Shell (RS)Architecture: The Svelte application contains zero domain business logic. It operates entirely as an API consumer over HTTP/3.State Management: Ephemeral UI state only. It reacts to data fetched from the Axum backend's CQRS read models.Justification: Implementing a Functional Core in TypeScript would create logic duplication and increase the Javascript bundle size ("carb bloat"), degrading performance on low-end devices on 3G networks.3. Universal Staff App (Flutter + Rust)Pattern: Full FCRS (Functional Core, Reactive Shell)The Functional Core (Rust): The librery-core crate is embedded natively via flutter_rust_bridge. It manages offline CRDT merges (Automerge), local command queues, and strict domain validation without a network connection.The Reactive Shell (Dart/Flutter): The Flutter UI layer is completely ignorant of library science rules. It merely captures user intent (e.g., a barcode scan), passes it across the FFI bridge to the Rust Core, and reactively repaints the screen based on the resulting State yielded by Rust.4. Power-User Terminal (Ratatui)Pattern: Full FCRS / FCISArchitecture: As a native Rust binary, it compiles the librery-core directly alongside the UI rendering loop.Execution: Keystrokes are captured by the terminal shell, mapped to Domain Commands, processed by the Core, and the resulting State triggers a terminal redraw. It operates with zero latency, independent of the Axum backend if connected directly to the local SQLite ledger.
