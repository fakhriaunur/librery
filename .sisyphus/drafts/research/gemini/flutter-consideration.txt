Librery: Frontend Evaluation (Flutter Alternative)1. Stats & Data Visualization (Maturity & Customization)For the Staff/Admin dashboards (circulation stats, fine revenues, cohort analysis), Flutter's visualization ecosystem is highly mature.Libraries: Packages like fl_chart, graphic (Grammar of Graphics implementation), and the commercial syncfusion_flutter_charts are incredibly robust.Customizability: Because Flutter paints every pixel via its Impeller/Skia engine, you can customize charts down to the micro-animation level far easier than fighting with CSS/SVG in traditional web wrappers.Verdict on Viz: Flutter easily passes the enterprise requirement for complex data visualization.2. The Patron OPAC: The "CanvasKit" DealbreakerUsing Flutter Web for the Patron OPAC actively violates our core mission of serving underfunded, low-bandwidth environments (e.g., rural schools outside Tasikmalaya).The Bundle Size TaxSvelteKit (Current Choice): Compiles to raw HTML/CSS and surgical JS. A complex OPAC page might be 50kb - 100kb over the wire. It loads instantly on a 3G connection.Flutter Web: Does not use native DOM elements. It ships its entire rendering engine (CanvasKit/WebGL) to the browser. A "Hello World" Flutter Web app starts at 1.5MB to 2.5MB before you even add library logic or cover images.The Performance & SEO Black HoleSEO (Search Engine Optimization): Libraries need their books to be discoverable on Google. Because Flutter Web renders the entire UI inside a single HTML <canvas> tag, it is a black box to web crawlers. Googlebot cannot easily index the catalog.Accessibility (WCAG): Screen readers struggle immensely with canvas-rendered text compared to native HTML DOM, violating institutional accessibility mandates.Verdict for Patrons: Hard Reject. Flutter Web is an application delivery vehicle, not a website builder. It is too "fat" and detrimental to public discovery.3. The Staff App: The Bridge vs. The Native CoreFor the Librarians, Flutter is a phenomenally strong contender for the mobile/desktop app, but it fundamentally changes our FCIS "Shared Core" architecture.The Integration Tax (flutter_rust_bridge)Dioxus (Current Choice): Is written in Rust. You simply use librery_core::ItemAggregate;. The Functional Core is natively compiled into the Dioxus UI. Zero friction.Flutter (Dart): Dart cannot run Rust natively. To use our pure Rust core for offline CRDT cataloging, we must use flutter_rust_bridge (FRB) or UniFFI.The Reality: FRB is excellent in 2026, but it means you are now maintaining a complex FFI (Foreign Function Interface) boundary. Every time you change a struct in the Rust core, you must regenerate the Dart bindings and cross the serialization bridge.4. Final Architectural VerdictIf the engineering team already possesses deep, senior-level Flutter expertise, Flutter is an acceptable choice for the Staff App (replacing Dioxus) via flutter_rust_bridge, as it delivers unparalleled cross-platform mobile performance and great data viz.However, under no circumstances should Flutter be used for the Patron OPAC. The massive bundle size, SEO destruction, and accessibility issues make it completely unsuitable for a public-facing, discovery-centric web platform. We must stick to SvelteKit (or raw HTML/HTMX) for the patrons to maintain our lean, high-performance mandate.
